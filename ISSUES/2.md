## 问题背景

当前 `main.py` 使用 OpenAI Agents SDK 的 `ShellTool` 为 Agent 提供只读 workspace 检查能力。在官方 OpenAI Responses API 语义中，模型应返回结构化 `shell_call` 事件，SDK 执行命令后继续 Agent 循环。

使用阿里云 DashScope OpenAI 兼容 Responses API（`qwen3.7-flash`）验证时，模型没有返回 SDK 可识别的结构化 `shell_call`，而是将 `<tool_call>` 作为普通正文输出。进程正常结束，但 ShellTool 未执行，Agent 无法实际读取和分析项目。

示例命令：

```bash
uv run python main.py \
  --question "分析这个项目" \
  --enable-reasoning true
```

实际输出末尾类似：

```text
[content]
我先查看一下项目的目录结构……
<tool_call>
```

## 原因

阿里云兼容 Responses API 支持自定义 `function` 工具并返回结构化 `function_call`，但当前文档未提供 OpenAI 原生 `shell` 工具类型。提示词只能影响工具选择，无法把普通文本稳定转换为 SDK 所需的 `shell_call` 协议事件。

## 建议方案

- 将本地只读 Shell 能力从 `ShellTool` 适配为 Agents SDK `function_tool`，使兼容提供商通过结构化 `function_call` 调用。
- 复用现有安全边界：
  - `_validate_read_only_command()`
  - `execute_read_only_shell()`
  - workspace 路径限制
  - 命令与 Git 子命令白名单
- 为函数工具提供严格、清晰的参数 schema；不要解析并执行正文中的 `<tool_call>` 标签。
- 确保工具输出通过标准 `function_call_output` 回传，使 Agent 可以继续生成最终回复。
- 如需同时支持官方 OpenAI 与兼容提供商，应通过明确的 provider/capability 配置选择工具实现，避免依赖提示词猜测协议能力。

## 验收标准

- [ ] 使用阿里云 DashScope OpenAI 兼容 Responses API 时，模型返回结构化 `function_call`，而不是正文 `<tool_call>`。
- [ ] Agent 能执行允许的只读命令并在工具结果返回后继续生成最终内容。
- [ ] 禁止命令、workspace 外路径及修改性 Git 子命令仍会被拒绝。
- [ ] `enable_reasoning=true` 时，工具调用前后的 `[reasoning]` 与 `[content]` 流式分区保持正确。
- [ ] 不通过解析模型正文中的 XML/JSON/`<tool_call>` 文本来执行命令。
- [ ] 增加结构化函数调用、工具结果续接、拒绝危险命令和兼容提供商事件的单元测试。
- [ ] README 说明受支持的 provider 工具模式及限制。
