## 问题背景

使用 OpenAI 中转节点运行 `main.py`，并开启 Reasoning 与本地工具调用时，首轮响应会产生彼此关联的 response items，例如：

- `reasoning`：`rs_...`
- `shell_call`：`sh_...`

Agent 执行 ShellTool 后会发起下一轮模型请求。当前续轮请求没有完整携带上一轮响应中的 response items，导致中转节点收到 `shell_call` 或工具输出时，找不到它依赖的 `reasoning` item，从而返回 400。

## 复现命令

```bash
uv run python main.py \
  --question "分析这个项目" \
  --enable-reasoning true
```

## 实际错误

```text
openai.BadRequestError: Error code: 400
Item sh_... of type shell_call was provided without its required
reasoning item: rs_....
```

该错误发生在工具执行后的下一轮请求，不是 `[reasoning]` / `[content]` 终端显示逻辑造成的。

## 期望行为

在 Reasoning 模式下进入工具续轮时，应满足以下任一可靠续接方式：

1. 将上一轮需要重放的完整 `response.output` items 按原始顺序加入下一轮 input，包括关联的 `reasoning` 与 `shell_call`；或
2. 使用中转节点支持的 `previous_response_id` / server-managed state，使服务端能够恢复上一轮完整上下文。

不得只提交孤立的 `shell_call`、`shell_call_output` 或其他依赖已遗漏 reasoning item 的响应项。

## 调查与实现建议

- 在不记录敏感正文的前提下，增加可选调试日志，输出每一轮请求 input item 的 `type`、`id`、`call_id` 和顺序。
- 对比官方 OpenAI 端点与中转节点返回的 response item 结构，特别检查 `provider_data`、reasoning item ID 和序列化行为。
- 检查 Agents SDK 在构造下一轮 input 时是否过滤了带 provider 元数据的 reasoning item，却保留了其关联工具调用。
- 评估并验证 `Runner.run_streamed(..., auto_previous_response_id=True)` 在中转节点上的支持情况。
- 仅在适用场景评估 `RunConfig(reasoning_item_id_policy="omit")`；该选项不能替代缺失的 reasoning item 本身。
- 对不支持完整 Responses 状态续接的中转节点给出明确错误或兼容配置，不应静默生成不完整请求。

## 验收标准

- [ ] Reasoning 开启且模型调用 ShellTool 时，工具执行后的下一轮请求不再出现缺少关联 reasoning item 的 400。
- [ ] 手动重放模式下，上一轮需要的 `reasoning`、工具调用及工具输出按正确顺序出现在下一轮上下文中。
- [ ] `previous_response_id` 模式下，仅在 provider 明确支持并成功保存上一轮响应时启用。
- [ ] 无 Reasoning 模式的现有工具调用行为不受影响。
- [ ] 流式与非流式运行均覆盖多轮工具调用场景。
- [ ] 增加测试：构造 `reasoning -> shell_call -> shell_call_output -> next response` 序列，并断言续轮 input 完整且顺序正确。
- [ ] 增加测试：模拟中转节点返回带 `provider_data` 的 reasoning item，确保不会留下孤立工具调用。
- [ ] README 记录 OpenAI 中转节点对 Responses API、Reasoning 和 server-managed state 的兼容要求。
